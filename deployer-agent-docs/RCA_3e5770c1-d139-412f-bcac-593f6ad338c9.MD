# RCA — NOVA (asistan-nova) Production Auth Bypass

**Severity:** Critical — unauthorized access to a single-tenant personal assistant confirmed in production data.
**Deployment:** asistan-nova (`84390b59-2e6a-4689-a53a-03b6db15b6fd`)
**Custom domains:** novaasistan.com, www.novaasistan.com (both verified)
**Live URL:** https://asistan-nova.emergent.host
**Active run analyzed:** `3e5770c1-d139-412f-bcac-593f6ad338c9` (type=redeploy, trigger=secret_change, 2026-10-08 05:05→05:09:28)
**Deployed image:** `...customers-app@sha256:1ccd0caca85f92e08439d6df8eeb82c1d46766867e4d3d2ac626646deec7f392`

## Verdict (kesin tespit)

- **STALE production state = the backend BUILD/CODE.** The currently-live image (`sha256:1ccd0c…`, run `3e5770c1`) was built from source that **predates the security fix**. The fix the user describes is **NOT present** in the running build.
- **DEPLOY GEREKLİ: EVET (zorunlu).** The allowlist/403 code must be shipped. A redeploy of the current agent-env source is required — but only AFTER the preconditions below (fix present in source + secret + data cleanup), otherwise the same bypass persists.
- Secrets, DB connection, domain routing and OAuth are functioning; the bypass is **100% a stale-code problem**, not infra/routing.

## Evidence

### 1. Deployed code has NO auth gate (root cause)
Inspected the pulled source of the active run (`/app/scratch` in eph sandbox):

- **`backend/auth_policy.py` DOES NOT EXIST** in the deployed build. (`cat` → FILE NOT FOUND.)
- The expected 403 text (“NOVA, Yapay Zeka Sanatçısı Bora ÜNSAL'a özel…”), `ALLOWED_USER_EMAIL`, and any allowlist logic appear **nowhere** in the deployed backend — grep only matched `tests/` files and `.env`'s `ADMIN_EMAILS`.
- Deployed `backend/server.py` `/auth/session` (line 174) and `current_user` (line 156) perform **zero email/allowlist gating**:
  - `current_user`: checks only cookie signature → session exists → user exists. Raises **401** only ("Giriş gerekli" / "Oturum geçersiz…" / "Oturum bulunamadı" / "Kullanıcı bulunamadı"). **No 403, no allowlist.**
  - `/auth/session`: verifies the Emergent session, then **upserts ANY Google account** (`db.users.update_one(..., upsert=True)`), issues a cookie, returns the user. **No email check before session creation.**
- `grep '403'` over `server.py` → **no matches.** The pre-/auth/session 403 gate the user added is absent from this build.

→ Any valid Google account that completes Emergent OAuth gets a session and passes `current_user`. This exactly matches the reported bypass.

### 2. Production data confirms the bypass (live Atlas DB `asistan-nova-nova_asistan`)
- `users` = **5 docs**: `yapayzekasanatcisi@gmail.com` (the intended allowlisted account) **plus 4 unauthorized**: `perisusorg@gmail.com` (“Bora ÜNSAL (Tiyatral Nikah Sanatçısı)”), `gunselieylem@gmail.com`, `burakavci1975@gmail.com`, `nexiauo@gmail.com`.
- `sessions` = **11 docs**, across **3 distinct `user_id`** currently (Google subs `106153980006385211736`, `101637821515513039843`, `101825400382449570936`). Sessions key on `user_id` (Google sub), not `user_email`.
- `google_tokens` = **1 doc only.** This is why every logged-in user saw *Bora's* NOVA/Workspace data: there is a single stored Google token and the integration is **not isolated per authenticated user** — a secondary data-isolation defect that remains even if only the allowlist is added.

### 3. Secrets (production, active run)
- `ALLOWED_USER_EMAIL` is **NOT present** in the production secret set at all. Present/related: `ADMIN_EMAILS` (non-empty). `MONGO_URL`, `DB_NAME`, `GOOGLE_CLIENT_ID/SECRET`, `SESSION_SECRET`, `TOKEN_ENCRYPTION_KEY`, `EMERGENT_AUTH_DATA_URL` all present & non-empty.
- If the new allowlist code reads `ALLOWED_USER_EMAIL`, it **must be added before the fix deploy** or the gate will be misconfigured. (Deployed `.env` hardcodes `ADMIN_EMAILS="yapayzekasanatcisi@gmail.com"` — confirm the new code's source of truth.)

### 4. Routing / live behavior (healthy)
- `/api/auth/me` on the live host → **401 `{"detail":"Giriş gerekli"}`** (correct for unauthenticated). This proves API routing to the K8s backend works; the failure is strictly the missing authorization layer for *authenticated* users.
- `CORS_ORIGINS` includes novaasistan.com / www.novaasistan.com. Note: deployed `.env` `FRONTEND_URL` and `GOOGLE_REDIRECT_URI` still point at `asistan-nova.preview.emergentagent.com` (config smell, not the bypass cause).

### 5. "Eski session bypass" question
Old sessions ARE a live bypass vector: the 11 existing session cookies remain valid for 7 days (`max_age=60*60*24*7`). Even after deploying the allowlist, `current_user` will still accept a pre-existing session for a non-allowlisted user **unless** the new code re-checks the email on every request AND the stale session/user rows are purged. Both are required.

## Required remediation (in order)

1. **Ship the fix (Code / deploy).** Confirm `backend/auth_policy.py`, the `/auth/session` pre-gate 403, and the central `current_user` allowlist check are present in the **current agent-env source**, then redeploy. The live build does not contain them.
2. **Secret (User).** Add/verify `ALLOWED_USER_EMAIL` (expected `yapayzekasanatcisi@gmail.com`) in Deployment → Secrets if the new code consumes it; ensure the allowlist’s source of truth matches.
3. **Purge + invalidate (User / DB).** Delete all `sessions` docs (invalidate every live cookie), and delete `users` / `google_tokens` records not belonging to the allowlisted account (remove the 4 unauthorized users and any of their tokens). Do this via DB Manager / E1 — not deployable from code alone.
4. **Verify data isolation (Code).** Fix the single-shared-`google_tokens` design so Workspace/Google data is scoped to the authenticated user, not a shared admin token.
5. **Re-verify after deploy:** authenticated non-allowlisted account must receive the custom **403** before session issuance; `/api/auth/me` with a stale cookie must no longer return another user’s data.

## Reproduction note
Verified statically against the deployed build's pulled source in the eph sandbox (no app secrets injected, so live-OAuth flow not re-run). The absence of `auth_policy.py` and of any 403/allowlist in `server.py`, combined with 5 users / 3 session owners / 1 shared google_token in the production DB, is conclusive.
